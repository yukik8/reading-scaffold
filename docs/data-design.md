## 0. なぜ作り直すか

v1 のデータは「足場 θ を減らす制御ループが効いているか」を確かめるためのもので、その目的には合っている。
読書アプリとしての資産(記録層)は、その脇に付いたログに留まっていた。

1. **単位がセッションと URL しかない。** 本を10回に分けて読んでも、残るのは読了率の最大値だけ。
   「この日は p.40→62 を読んだ」が復元できなかった
2. **本人が起点のものほど薄い。** 自分からの問いはダッシュボードに件数だけ。問いを投げたときに
   選んでいた箇所は保存していなかった。システムが作ったクイズの○×が一番目立っていた
3. **痕跡どうしがつながらない。** クイズも問いも本にぶら下がるだけで、「本のどこで」の軸がない
4. **時間で育たない。** クイズは出題時の1回きり。正答率は「その場で答えられたか」で、
   1週間後に覚えているかは測っていない

ダッシュボードの上半分(帯・自立の推移・週次目標・補助なし時間)は θ の話で、卒業すると止まる。
卒業後も使い続ける理由は記録層のはずなので、記録層を「本」と「箇所」を単位に組み直す。

## 1. 大原則

### 3層は変えない

| 層 | 何のため | URL/本文 | 行き先 |
|---|---|---|---|
| 計測層 `events` `sessions` | 制御器・評価 | 持たない(ドメインのみ) | 週次の派生指標だけ(計画)匿名でサーバへ |
| 制御層 `state` | θ の現在地 | 持たない | ローカルのみ |
| 記録層 `pages` `readings` `quizzes` `quiz_attempts` `questions` (計画)`passages` `marks` `recalls` | 本人の資産 | **持つ** | **ローカルのみ** |

- 増やすのは記録層だけ。計測層は意図的に貧しいまま(ドメインのみ)にする
- 本の中の位置(ページ)は記録層に置く。計測層の `events` には入れない

### 単位を「本」と「箇所」にする

- **本** = `pages` の1行。Play ブックスは URL の `id=` で1冊を特定する(`session.js` の `pageKey`)。
  ストア名は `pages` のまま据え置く(IndexedDB はストアの改名ができず、コピーの手間に見合わない)
- **読んだ区間** = `readings` の1行。1セッション=1区間
- **箇所** = 本の中の位置。ページ番号で表す(Play ブックスのページ表示「N / M」。文字の大きさや
  ウィンドウ幅で変わらないことは確認済み)。見開き「4-5 / 17」は後ろのページを採る
- **本人が起点の痕跡**(問い・選んだ箇所・主張)を、システムが作ったもの(クイズ)より上に置く

## 2. ストア

### 2.1 pages(本)— 既存+キャッシュ2項目

```
{
  page_id,              // 正規化URLの SHA-256。Play ブックスは .../books/reader?id=<本のid>
  url, title, domain, lang, word_count, summary,
  first_read_at, last_read_at, read_count, total_read_ms, best_completion_pct,
  book_position,        // v4: { page, total } 最後に読んだ位置(readings からの導出キャッシュ)
  finished_at,          // v4: 初めて最後のページに着いたセッションの終了時刻
}
```

- `title` はタブのタイトルから後ろの「 - Google Play Books」(日本語 UI では「ブックス」)を除いたもの。
  著者名はタブのタイトルに含まれないので持たない
- 集計値は従来どおり導出キャッシュ。真実は `sessions` と `readings`

### 2.2 readings(読んだ区間)— v4・実装済み

```
{
  session_id,           // keyPath。sessions と1対1
  page_id,              // 本
  date, started_at, ended_at,
  range: { from, to, furthest, total },  // 本のページ。開始時・終了時・最も先まで・総ページ
  page_turns,           // ページ送りの回数(events の page_turn から数える)
  read_ms,              // sessions と同じ値(記録層だけで本ごとのペースを出せるように複製)
  reached_end,          // 最後のページまで着いたか
}
```

- Play ブックスで、ページ表示が一度でも読めたセッションだけが書く
- これで出せるもの: 本ごとの「いつ・どこを読んだか」、本ごとのペース(ページ/分)、読み終えるまでの残り時間
- 位置はセッション中 `chrome.storage.local` の別キー(`bookPosition`)に置く。現在のセッション本体は
  複数のハンドラが読み書きして上書きし合いうるので、そこに相乗りさせない

### 2.3 quizzes / questions — v4 で位置と選択を足す

```
quizzes   { ..., book_page }               // 出題した時点で開いていたページ
questions { ..., book_page, selection }    // 問いを投げた時点のページと、選んでいた文字列(なければ null)
```

- `selection` は本人が指した箇所そのもの。今まで捨てていた
- `book_page` があれば、クイズと問いを本の中の位置に並べられる(§4 の帯)

### 2.4 passages / marks / recalls — 計画

architecture-v1 §7 で計画していた `memory_items` は、この3つに分けて置き換える。

```
passages  箇所。痕跡をすべてここにぶら下げる
  { passage_id, page_id, book_page, excerpt(短く), hash }

marks     本人が起点の痕跡(余白への書き込み)
  { mark_id, passage_id, page_id, session_id,
    kind: 'question' | 'selection' | 'claim', text, answer?, created_at }

recalls   思い出した記録(quiz_attempts を広げたもの)
  { recall_id, passage_id | mark_id, kind: 'quiz' | 'recall',
    prompt, result, answered_at, days_since_read }
```

- 「一番大事だった主張」(architecture-v1 §7 の想起カード)は `marks` の `claim`、後日の再想起は `recalls`
- 既存の `questions` は `marks(kind=question)`、`quiz_attempts` は `recalls(kind=quiz)` に寄せる。
  移行は表示を作るときに行う(今は位置と選択を取りこぼさないことを優先)
- 原則は v1 と同じ: 本人が想起したものだけを資産にする。LLM は要約を書かない

## 3. 制御器との関係(変えない)

- **記録層は制御器に入れない。** 制御器の入力は行動シグナル(read_ms / escapes / away / return /
  completion / end reason)だけ。クイズ正誤・問いの数・想起の結果・読んだページ数は入れない
- 理由は v1 と同じ: 理解やエンゲージメントを入力にすると、「簡単な問題を出せば θ が下がる」
  自己目的化の回路ができる
- `recalls` は評価(理解のガードレール)と記録にだけ使う。合格ライン(architecture-v1 §10)の
  「理解の非劣化」をクイズ正答率から想起率に替えるかは、データがたまってから決める

## 4. ダッシュボードで出すもの(1・2 は v0.20 で実装)

すべて事実の表示。可変報酬・比較・警告・催促はしない(記録カテゴリのルール)。

1. **本棚** — 本ごとに今の位置(`book_position`)と、読み終えるまでの残り時間
   (残りページ ÷ その本での自分のペース)。読み終えた本は `finished_at` で分ける
2. **1冊の帯** — 本の長さを横棒にし、`readings` の区間を読んだ回数の濃淡(1回・2回・3回以上)で
   塗る。上の2段に問い(輪)とクイズ(点)を `book_page` の位置に打ち、しおりで今の位置を示す。
   開くと「余白」(問い・選んだ箇所・クイズをページ順に)と「読んだ日」(区間ごとに一行・同じ横軸)が出る。
   位置の記録がない古い問い・クイズは余白の末尾に「—」で並べる
3. **時間がたっても残っていること** — `recalls` の7日後・30日後の結果。その場の正答率の代わり
4. **繰り返し気にしているテーマ** — 本をまたいで問い・主張をつなぐ(§6 の Open Question 1 が決まってから)

θ の節(帯・自立の推移・週次目標)は残すが、本の節より下に置く。本のクイズは余白に移したので、
独立した一覧には Web 記事のものだけを出す(記事が無ければ節ごと隠す)。

## 5. 削除とエクスポート

- 全消去は1タップのまま、全ストア(v4 で8ストア)と storage を空にする
- エクスポート(JSON)に `readings` を含める。新しい項目は既存ストアの中なので自動で入る

## 6. Open Questions

1. テーマ付けに LLM を使うか。使うなら「言葉で教えない」原則との線引き
   (タグを付けるのは「教える」ではない、と置けるか)
2. `selection` を問いのとき以外にも取るか(ハイライト)。取るなら UI が要り、道具カテゴリの機能になる
3. 想起カード・再想起を出す場所とタイミング(architecture-v1 §13 の 2 と同じ)
4. 既存の `questions` `quiz_attempts` を `marks` `recalls` へ移すときの移行手順
