# データ設計ノート(2026-08-16)

読書履歴・クイズ・計測・制御を、全体としてどう保持するかの設計。実装前の合意用。

## 0. 大原則: データは3層に分かれる

reward-design.mdの「演出/記録」二分法と同じ発想で、データも役割ごとに層を分ける。
**層ごとにプライバシー特性と寿命が違う**ことが、この設計の中心。

| 層 | 何のため | 中身の性質 | URL/本文 | 寿命 |
|---|---|---|---|---|
| **計測層** | タペリング制御器・Mirror | 統計的・匿名的 | 持たない(ドメインのみ) | 週次集計後は本質的に使い捨て |
| **制御層** | θの現在地(連続値) | 単一レコード | 持たない | 常に上書き |
| **記録層**(新設) | 読書メモリ = 本人の資産 | 具体的・個人的 | **持つ**(URL・タイトル・クイズ本文) | 永続。本人だけのもの |

- 計測層が意図的に貧しい(ドメインだけ)のは変えない — サーバへ出る週次派生指標の
  匿名性の根拠なので
- 記録層は逆に意図的に豊かにする。ただし**ローカルのみ・サーバへは一切出さない**。
  ここは「複製不能な資産」であり、卒業(θ=0)後も残り続ける唯一の層
- 記録層には可変報酬を載せない(記録カテゴリのルール)。Mirror・ライブラリ表示・
  将来のペットはこの層だけを読む

## 1. ストア一覧(IndexedDB v2)

既存3ストアは変えず、記録層に3ストアを足す。

```
[計測層] events        既存: append-onlyの生ログ(制御器とデバッグの真実)
[計測層] sessions      既存 + page_id を追加(記録層への橋。ローカル内のみ)
[制御層] state         既存: { theta(連続値), success_streak, fail_streak, ... }(2026-08-16 Level廃止)

[記録層] pages         読んだもの(1 URL = 1レコード)
[記録層] quizzes       出題されたクイズ(問題そのもの)
[記録層] quiz_attempts 回答の記録
```

### pages(読んだものの台帳)

```
{
  page_id,            // URLの正規化ハッシュ(クエリ・フラグメント除去後)
  url, title, domain, lang,
  word_count,
  summary,            // ページ概要。v0はnull(LLM要約は後続 — 本文送信は/quizと同じ経路)
  first_read_at, last_read_at,
  read_count,         // セッション数
  total_read_ms,      // 累計読書時間(質問にあった「どれくらい読み続けられたか」はここ+sessions)
  best_completion_pct
}
```

- 集計値(read_count以下)は sessions からの導出キャッシュ。真実は events/sessions
- 1セッション=1記事(v0設計)なので、セッション終了時に該当pageへ積むだけでよい

### quizzes(クイズは独立して保持する — 質問への答え: 別で持つのが正しい)

```
{
  quiz_id,
  page_id,            // どの記事から出たか
  paragraph_hash,     // 出題元段落(サーバのキャッシュキーと同じハッシュ)
  paragraph_excerpt,  // 冒頭80字程度。後から「どこの話だったか」を思い出せる最小限
  question, choices[3], answer_index,
  created_at
}
```

別テーブルにする理由:
1. **1記事に複数クイズ**が自然に増える(1セッション1問でも再読で増える)
2. **再利用できる**: 後日の復習出題(spaced repetition)は記録層のクイズを
   そのまま再演できる — 理解連動Micro Contentの自然な発展
3. 問題(不変)と回答(毎回変わる)は寿命が違う → attempts をさらに分ける

### quiz_attempts(回答の記録)

```
{
  attempt_id,
  quiz_id, page_id, session_id,
  answered_at,
  chosen_index, correct,
  latency_ms          // 表示から回答まで。迷いの指標(分析用・制御には使わない)
}
```

「その人が何を読んで・どういうクイズに正解できたか」はこの3ストアのJOINで出る:
pages → quizzes → attempts。「知識を得たか」のv0の代理指標は attempts.correct。
本物の知識表現(ハイライト・要点抽出)は将来の notes ストアとして予約(v0では作らない)。

## 2. 既存層との接続

- **sessions に page_id を1フィールド追加**するだけ。セッション終了時に
  pages を upsert して集計を積む。読書時間を「ページに付随させるか」への答え:
  真実は sessions(セッション単位)に置いたまま、pages に累計を持つ(両方)
- events は変更なし。quiz_answered イベントに quiz_id を足す(生ログからも辿れるように)
- 週次派生指標(サーバ送信)は**変更なし**。記録層は1バイトもサーバに出ない

## 3. 制御器との関係(重要な線引き)

**クイズの正誤は制御器に入れない。** 理由:

1. 既存の不変条件「エンゲージメント指標を制御器の入力にしない」の同類。
   正答率を入力にすると「簡単な問題を出せばθが下がる」という
   自己目的化の回路ができる(スロットマシン化の変種)
2. 制御器の入力は今まで通り read_ms と escapes だけ。クイズは演出と記録の住人

ただし「理解シグナルとしてのクイズをW3以降の制御器v2で使うか」は
Open Question として残す(使うなら出題難易度の統制が先に必要)。

## 4. 削除の設計

- 既存の「全部消す」は6ストア全消去のまま(1タップ全消去の約束は守る)
- 層が分かれたので「計測だけ消す(記録=資産は残す)」を将来追加できる。
  逆(記録だけ消す)も。v0は全消去のみでよい

## 5. 実装順の提案

1. DB v2 マイグレーション(onupgradeneededで3ストア追加、既存データ無傷)
2. セッション開始時: URL正規化 → page_id、title取得 → pages upsert
3. セッション終了時: pages に read_ms / completion を積む
4. クイズ表示時: quizzes へ保存。回答時: quiz_attempts へ保存
5. (後続) Mirrorに「ライブラリ」ビュー: 読んだもの一覧+クイズ正答
6. (後続) summary生成、notes/ハイライト、復習出題、ペット

## 6. Open Questions

1. summary生成のタイミング(読了時に自動? 本文送信が増えるので明示操作にする?)
2. 同一URLの再訪でセッションを跨いだ「続きから読んだ」をどう表現するか
   (v0: pagesの累計で十分とする)
3. クイズ正誤を制御器v2の入力にするか(上記の通り当面しない)
4. 記録層のエクスポート形式(JSON / Markdown。資産なので持ち出せるべき)
